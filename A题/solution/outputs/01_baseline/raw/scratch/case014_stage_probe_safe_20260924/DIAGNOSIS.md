# case_014 单核评估耗时定位（探索性）

2026-09-24。依据同目录 `manifest.json`、`probe.py`、`stacks.log`。原始评估代码、数据和配置只读且哈希不变；探测运行使用独立副本，不能用作正式成绩。

## 已观察到

- 先前原始入口的 60 秒、300 秒运行均超时，本次副本探测预算为 45 秒，结果仍为 timeout。
- 本次 step1 约 0.218 秒、step2 约 0.976 秒、构建扩展图约 0.002 秒，`prepare_step3_execution` 约 11.242 秒完成。这些墙钟值受环境和并发任务影响，仅用于定位阶段。
- 核内排布完成后，后续多次 Python 栈采样落在 `multicore_cut_evaluate_problem_1.py` 的 `retire` 中，尤其是第 372 行对当前 Task 整份 `seq` 重建 `task_items` 的列表推导；也采到事件循环其他位置。
- 当前源码在每轮事件中，对每个 active Task 重建完整操作列表，再用 `all(...)` 检查是否全部结束。一个大 Task 会反复扫描大量操作，属于明确的重复工作。

## 解释与边界

现有证据支持“全局事件模拟的 Task 完成检查存在性能热点”，不支持“卡在 step1/step2”，也不能认定数学结果错误或死循环。对于一个含 M 个操作、经历 E 轮事件的活跃 Task，仅重建列表就可能带来 O(E×M) 的工作；尚未测定此处占总时间的精确比例。

本轮只定位，不修改原始程序，也没有用改写版模拟结果补充正式单核分母。后续可先在独立副本中检验增量完成计数等优化是否保持所有事件结果一致；修改正式评估器前仍需遵守项目的讨论规则。
