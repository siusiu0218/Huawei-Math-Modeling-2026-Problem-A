# A 题解题工作规则

本文件适用于 `A题/solution/` 下的解题工作。以下六条规则已由用户逐项确认；未经讨论，不得自行修改。

## 1. 原始材料保护

- `A题/code/`、`A题/data/`、`A题/docs/`、原始题目及附件均作为只读材料。
- 自编算法、实验脚本和结果统一放在 `A题/solution/`。
- 发现评估器疑似存在问题时，先记录证据并与用户讨论，不直接修改。
- 探索性验证使用独立副本，其结果与正式评估结果分开保存和标注。

## 2. 自主执行范围

- 在已确定的任务范围内，可以自主编写代码、运行测试、开展实验和修复问题，无须逐次确认。
- 改变研究目标、扩大任务范围、删除已有成果、安装或升级环境依赖，以及对外提交或发布前，需要先与用户讨论并取得同意。
- 效果不佳时，可以调整范围内的算法实现，但必须记录调整理由和实测结果。

## 3. 完成标准

- 区分“原型验证”和“正式完成”。原型可以只跑部分用例，但必须标明实际覆盖范围。
- 正式完成某一问，必须覆盖题目要求的全部用例和核数，使用原始评估器与固定配置验证，并保存调度方案、指标和复现命令。
- 失败、超时或未通过的用例必须如实列出，不得悄悄排除或将未完成的全量验证标为完成。
- 代码能运行不等于优化有效；优化效果必须与明确的基线比较。

## 4. 算法版本与实验数据管理

算法版本、实验编号和结果位置必须一一对应，不能只靠文件日期辨认。

第一问与第二问可以复用 `src/` 中的通用算法代码，但实验入口、评估器、配置和运行记录必须按问题编号区分。第一问的正式全量结果保留在 `outputs/08_full/`；第二问的报告、图表及每次实验的方案、指标和日志统一放在 `outputs/09_problem2/`，原始记录使用 `raw/problem_2/<算法版本>/<实验编号>/`。第二问每次新运行使用独立实验编号，不覆盖第一问结果，也不将两问的指标合并统计。

### 固定目录

```text
solution/
├─ src/                              自编算法
├─ tests/                            合法性和关键边界测试
├─ experiments/                      实验入口及实验配置
│  └─ INDEX.md                       实验总目录
└─ outputs/
   └─ 01_baseline/                   按解题步骤分类；其他步骤见 outputs/README.md
      ├─ 主要报告.md                  可直接浏览的报告和图表
      └─ raw/                        完整原始运行记录
         └─ problem_1/v001/exp001_20260924_baseline/
            ├─ manifest.json         版本、参数、用例、核数、运行状态等
            ├─ source/               本次算法及运行脚本快照
            ├─ plans/                调度方案
            ├─ metrics/              逐用例指标及汇总表
            ├─ logs/                 运行日志和失败记录
            └─ figures/              本次结果生成的图表
```

以上实验路径为命名示例，不表示该实验已经运行。目录按实际实验创建。

### 结果保存位置

- 所有实验结果、报告、图表、调度方案、指标和运行日志统一保存到主工作目录 `D:\workspace\HuaWei\A题\solution\outputs\`，按解题步骤分类；原始记录保留 `raw/problem_<问题编号>/<算法版本>/<实验编号>` 结构，临时诊断保留 `raw/scratch/` 结构。新实验的步骤路径由 `experiments/result_paths.py` 统一确定。
- 即使任务在 Codex worktree（如 `C:\Users\siu\.codex\worktrees\...`）中执行，也要将结果写入上述主工作目录，并在结束前核对文件已保存。不要把 Codex worktree 当作结果的最终存放位置。
- 实验入口若默认按当前工作目录写文件，运行前应显式指定主工作目录的输出路径；不要仅在 worktree 中生成结果后就报告完成。

### 命名与追溯

- 算法代码改变就递增版本号，例如 `v001` → `v002`；只改变实验参数则使用新的实验编号。
- 每次正式实验使用独立目录，按 `outputs/<解题步骤>/raw/problem_<问题编号>/<算法版本>/<实验编号>_<日期>_<简短说明>/` 存放。
- `manifest.json` 记录问题编号、算法版本、实验编号、参数、随机种子（如有）、用例范围、核数、运行时间、运行状态和复现命令。
- 保存本次算法及运行脚本快照，确保后续代码变化后仍能追溯本次结果。
- 调度方案文件名包含用例和核数，例如 `case_001_n2.json`。
- 逐用例结果表每行标明问题编号、算法版本、实验编号、用例和核数；汇总表明确汇总范围，不混淆逐用例数据与汇总数据。
- 图表标明算法版本与实验编号；论文中的每个数字和图表都能追溯到对应实验。
- `experiments/INDEX.md` 登记每次实验的目的、算法版本、实验编号、状态和结果路径；失败或中断也必须登记。
- 新实验不覆盖旧的正式结果。临时调试仅放在对应步骤的 `raw/scratch/`，不混入正式统计。

## 5. 文档与进展同步

- 开始任务前读取本文件和 `CONTEXT.md`。
- 每完成一个阶段，更新 `CONTEXT.md`，明确区分“已验证、待验证、已放弃”，记录关键决策、当前选定的算法版本、对应实验路径和下一步。
- 运行命令或目录结构改变时，同步更新 `README.md`。
- 不把设想、计划或未运行的实验写成已完成事实。
- 本文件中已确认的规则，未经用户讨论同意不得自行修改。
- 当前初始化约定：本次仅写入 `AGENTS.md`；`README.md` 和 `CONTEXT.md` 保持空白，初始内容待双方商讨确定。

## 6. 公平比较与优化证据

- 以题目规定的 Makespan 为主要指标，同时报告额外搬运量、算法运行时间，以及第三问的 Cache 命中率。
- 算法之间使用相同的用例、核数和评估配置，并披露搜索时间或候选方案数量。
- 调参用例与检验泛化效果的用例分开；最终按题目要求报告全部用例。
- 不得针对用例编号硬编码方案，不得只挑提升的结果报告。
- 新增优化必须通过对照实验确认收益；未验证或未观察到收益时如实说明。
